# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

npm workspaces monorepo (`server`, `client`). Run everything from the repo root. Node >= 22.12 is enforced (`engine-strict`); CI uses Node 24.

```bash
npm run demo           # API on :4000 against an in-memory MongoDB with sample data + Vite on :5173
npm run dev            # same, but against MONGODB_URI from server/.env (Atlas)
npm test               # server API tests (node:test, test/**/*.test.js)
npm run test:e2e       # Playwright browser tests (e2e/)
npm run lint           # ESLint
npm run format:check   # Prettier check; CI fails on unformatted files
npm run seed           # load the sample catalog into MONGODB_URI (skips if products exist; -- --force replaces)
npm run backup         # save MONGODB_URI's database to ~/Bazaar-backups/<db>-<date-time>/ (never inside the repo)
npm run restore -- <folder> [--yes]   # without --yes: say what it would replace; with: back up first, then restore
```

Single tests: `npm test -w server -- --test-name-pattern="sorts by price"`, `npx playwright test -g "paginates"`.

CI runs lint → format:check → test → build → test:e2e. Prettier: single quotes, 120 columns.

The API uses port **4000** (not 3001) so it can run next to the user's task-manager project.

Project skills in `.claude/skills/`: **run-store** (launch and check the app in the browser), **add-feature** (conventions and checklist for new stages), **atlas-troubleshooting** (diagnose the Atlas connection without revealing `server/.env`). Project agent in `.claude/agents/`: **demo-verifier** (read-only tester that runs the demo, checks the UI and reports PASS/FAIL).

## Hooks

`.claude/settings.json` runs these scripts from `.claude/hooks/` (Node, no dependencies):

- **guard-env.mjs** (before Read, Grep, Bash): blocks reading or printing `server/.env` and its copies (`cat`/`head`/plain `grep`/Read tool, `echo $MONGODB_URI`, `console.log(…MONGODB_URI…)`), `git add` of an env file, and any `git commit`/`push` while an env file is staged or tracked. Count-only and masked checks (`grep -c`, `wc`, `test -f`, awk structure listings) stay allowed for the atlas-troubleshooting skill. It is a guardrail for common commands, not a sandbox.
- **confirm-destructive.mjs** (before Bash): asks the user before `npm run seed -- --force` (replaces the Atlas catalog), `npm run restore` (replaces the Atlas data with a backup), `npm run reset-two-step` (switches off an account's two-step login), force pushes (`--force`, `-f`, `--force-with-lease`, `+refspec`) and `git reset --hard`.
- **format-file.mjs** (after Edit, Write): runs the repo's Prettier on the changed file; on a syntax error it reports Prettier's message back instead of failing silently.

If a hook blocks something you need, explain why to the user rather than working around it. Review or disable hooks with `/hooks`.

## Architecture

The store is being built in stages (see README): catalog, accounts/cart/checkout, the admin panel (opening on a sales dashboard), Razorpay payments (test mode), reviews/wishlist, product variants (sizes/colours), returns and exchanges, order emails (and new-order alerts for admins) and password reset are all done, and it is deployed on Render. Ideas not built yet, and ones set aside, are in `ROADMAP.md`: when one is built, move it to its Done table with the commit; when suggesting what's next, add new ideas there.

**Server** (`server/src/`): `createApp(ctx)` in `app.js` mounts one router per area (`routes/*.js`), each a function of `ctx = { db, client, config, razorpay, mail }` (MongoDB `Db`, `MongoClient` for sessions/transactions, config, Razorpay client or null, mail client). `index.js` loads config (`config.js` reads the gitignored `server/.env`; real env vars win), connects (`db.js` also creates indexes), and serves `client/dist` in production.

- **Money:** every price is an integer number of **paise**, in the database, the API and client state. Format only at display time (`client/src/format.js`). Never store rupees or floats.
- **Validation:** request input goes through zod schemas via `parse()` in `http.js`, which turns the first issue into a 400. Handlers are async (Express 5 forwards rejections) and throw `HttpError(status, msg)`.
- **Ids and URLs:** documents use MongoDB ObjectIds (exposed as hex strings); products and categories are addressed by unique `slug`.
- **Search** (`searchTerms`/`searchStages` in `routes/catalog.js`): each word (lower-cased, plural `s`/`es` dropped, plus a few `SYNONYMS` such as phone → mobile) must match the title, brand, a highlight or the category name, from the start of a word (escaped regex), so "book" doesn't find "Chromebook". All words must match: no partial results. With a search, the `relevance` sort ranks by `searchScore` (per word: title or brand 4, category 3, highlight 1; the whole phrase in the title +5), then popularity (`rating.count`); without one, it is popularity, labelled "Popularity" instead of "Relevance" in the UI. Search is a regex scan, fine at this catalog size. With no results for `q`, `GET /products` adds `suggestion` (`correctSearch()`: each word that isn't the start of a known word, plural or synonym is replaced by the closest word in `storeWords()`, shown products' title/brand/highlight words and category names of 3+ letters, cached a minute per db; allowed edits (`editDistance`, with swaps) 1 for 3–5 letters (3 only with the same first letter) and 2 from 6, compared to whole words and to the start of longer ones; ranked by edits, whole word, first letter, frequency) only when that search counts > 0 with the same filters. `GET /search/suggest` reuses `searchStages` (which also returns `matchingCategories`) for the header's `SearchBox` combobox: suggestions are fetched 150 ms after typing stops (the timer is set in the change handler, not an effect), from 2 characters; the input's role is `combobox`, so e2e tests find it with `getByRole('combobox', { name: 'Search products' })`. The brand facet is computed without the brand filter so other brands stay selectable.
- **Inactive products** (`active: false`) are hidden from listing and detail endpoints, and refused at checkout. Admins never delete products (orders reference them), only hide them.
- **Admin** (`routes/admin.js`): `router.use('/admin', requireAdmin)` guards everything under `/api/admin` (401 logged out, 403 customers). Product and category slugs are made once from the title/name (`slugify` from `seed.js`, numbered on clashes) and never change. Products without images get a generated SVG placeholder (`image()` from `seed.js`). Order search by number matches the end of the id via `$expr`/`$toString` (a scan; fine at this size).
- **Payments** (`payments.js`, `razorpay.js`, `routes/payments.js`): Razorpay over plain `fetch` (no SDK); `config.razorpay` is null without keys (COD only) and startup refuses non-`rzp_test_` keys. An online order is created `awaiting_payment` with stock reserved and `expiresAt` (30 min); the Razorpay order is created after the transaction (on failure ours is cancelled). It becomes `placed` only via `confirmPayment()` (checks order id, amount, captures if `authorized`), reached from the browser (signature verified), "check again" (`syncPayment`), or the webhook (raw body kept by `express.json`'s `verify` for the HMAC) — all idempotent. `expireUnpaidOrders` runs every minute from `index.js` and syncs with Razorpay before cancelling (`cancelledBy: 'system'`); `cancelOrder` refunds paid orders after its transaction (`refundPayment` claims `payment.status` first; failures → `refund_failed`, admin retry). Razorpay pays refunds from the account balance, which is short of each payment by its fee, so a full refund it can't cover comes back as a bare "invalid request sent" 400 (seen with real test keys); `refundError` therefore names Razorpay's reason plus a balance hint, and only admin responses include it (`toOrder(doc, { admin: true })`). A refund Razorpay accepted is still `pending` on its side for days, so the UI says "refund started". A payment arriving for a cancelled order is refunded. `payment` is `{ method: 'cod' }` or `{ method: 'razorpay', status, razorpayOrderId, … }`; old orders stored the string `'cod'` (normalized in `toOrder`). `HttpError(…, { expose: true })` lets a 502 message reach the client.
- **Reviews** (`routes/reviews.js`; admin list/hide in `admin.js`): only customers with a `delivered` order containing the product can review it, one review per (product, user) (unique index); `author` is a shortened name ("Asha R."). The sample catalog's ratings have no review documents, so `changeRating()` keeps them as `ratingBase` (copied from `rating` on the first change) plus `reviewStats` `{ sum, count }` of **visible** reviews, and recomputes `rating` in one update pipeline; every review write, delete and admin hide/show runs it in the same transaction (`inTransaction`). Hidden reviews stay hidden when edited and leave the rating; only a real hide/show state change moves it.
- **GST** (`gst.js`, `routes/gstSettings.js`, stage 38): `settings` `{ _id: 'gst', enabled, gstin, legalName, address, state, defaultRate }` and `categories[].gst { rate, hsn }` (no rate: the default). `POST /orders` calls `gstForOrders()` inside its transaction: with GST on, items get `gstRate`/`hsn` and the order `gst` (store details, `stateCode`, `deliveryRate` = highest item rate), so invoices never change with later settings. `toOrder` returns `gstInvoice(doc)` (null without `order.gst`): lines are tax-inclusive values split as `taxable = round(value × 100 / (100 + rate))`, tax = the rest, CGST `floor(tax/2)` + SGST the remainder when `findState(address.state).code === stateCode`, else IGST; a coupon's discount is prorated over items in whole paise (largest remainders; a `free_delivery` coupon reduces the delivery line), so lines always add up to `total`. Rates allowed: `GST_RATES` (GST 2.0 slabs). GSTINs are checked with the base-36 check character (`gstinCheckChar`, verified against the published 27AAPFU0939F1ZV) and must start with the chosen state's code. The address schema's `state` must be one of `INDIAN_STATES` (36, with GST codes; `findState()` accepts case/spacing/old names like Orissa) and is stored by its proper name; `client/src/states.js` has the same names for the form's `<datalist>` (a test compares them). The tax invoice shows paise (`formatAmount`), its totals are a separate table (on phones the HSN/rate/qty columns fold under the item), and `e2e/gst.spec.js` switches GST off again because `invoices.spec.js` runs after it on the shared server.
- **Questions** (`routes/questions.js`, stage 37, collection `questions` `{ productId, userId, author, text, createdAt, answer: { text, by, at, updatedAt } | null, hidden }`): only answered, not hidden questions are public; `GET /products/:slug/questions` adds `waiting` (the visitor's own unanswered ones), so the client waits for the login check before loading. Asking: `takeHourlySlot('question:<userId>', 5)` plus at most 20 unanswered per user. The answer is set in an update pipeline, so its text goes in `$literal` (a leading `$` would be a field path) and `answer.at` keeps the first answer's time (`$ifNull`); the asker is emailed only on the first answer (`sendQuestionAnswered`, never throws). Answers and hides are in the activity log (area `questions`); the dashboard returns `questionsToAnswer` (`UNANSWERED`). The product page section is `#questions` (the email links there; it scrolls once loaded).
- **Review photos** (stage 44): `POST /reviews/photos` (in `routes/images.js`) stores a customer's JPEG/PNG in `images` with `kind: 'review'` after `stripMetadata()` (`imageMetadata.js`: drops JPEG APP1/APP3–13/APP15/COM segments and PNG tEXt/zTXt/iTXt/eXIf/tIME chunks, keeping JFIF, ICC and Adobe colour data; malformed files → 400); the hourly slot is taken only after the file checks pass. Reviews take `photos` (≤3 `/api/images/…` addresses, each an upload with `uploadedBy` = the reviewer and `kind: 'review'`); `imagesInUse()` counts `reviews.photos`, so unused review uploads go with the daily sweep. The client shrinks photos first (`photos.js`: `createImageBitmap` + canvas → JPEG ≤1600 px, quality stepped down to fit 1 MB), which also drops metadata and applies phone orientation. The questions form shares the `review-form` style, so tests pick the review form by its text.
- **Wishlist** (`routes/wishlist.js`): a `wishlist` collection of `{ userId, productId, addedAt }` (unique pair, ≤200 per user); hidden products are left out of the list, not removed. `GET /products/:slug` includes `wishlisted` for the logged-in visitor.
- **Order emails** (`emails.js` templates + `sendOrderEmail()`, `mail.js` Brevo client over `fetch`): sent after the change is saved, from the four status changes: `placed` (COD in `POST /orders`; online only in `confirmPayment()` when it actually moves the order, so repeats send nothing), `shipped`/`delivered` (admin status route), `cancelled` (inside `cancelOrder()`, after any refund, so it can say "refund started"; `notify: false` when Razorpay refused the order at checkout). `sendOrderEmail` never throws: a mail failure is logged and the order change stands. Without `BREVO_API_KEY` the client only logs subject and recipient; `demo.js` blanks the key so demo/e2e accounts are never emailed. Links use `config.mail.publicUrl` (`PUBLIC_URL`). **New-order alerts** for admins (`sendNewOrderAlert()`, `newOrderEmail()`) are sent right after the customer's `placed` email at both of its call sites, so online orders alert once and only when paid; recipients are `ADMIN_EMAIL` (`config.mail.adminEmails`, comma-separated) or, when unset, every `role: 'admin'` user, each sent separately so one bad address doesn't stop the rest. Tests use a recording stand-in (`t.mail.sent`, `t.mail.failNext()`).
- **Saved carts** (`routes/savedCart.js` + `client/src/cartSync.jsx`, stage 41): `carts` `{ _id: userId, items (ObjectIds), updatedAt, remindedAt? }`; `GET/PUT /cart/saved` (lines checked by `savedCartLines` from `orders.js`, which may be empty). The browser's `localStorage` cart stays the working copy; `CartSync` (inside `AuthProvider`) loads the saved cart on login and when the tab becomes visible, and PUTs changes 400 ms after the last one. `bazaar.cartOwner` (in `cart.js`) says whose copy the local cart is: none (a guest's) → merged into the saved one (`mergeCarts`, larger quantity); this user's → replaced by the saved one, unless `bazaar.cartUnsaved` is set: `cart.js` sets it on every customer change to an account's cart (not on `replaceCart`) and `CartSync` clears it once the PUT matches, so a change followed by a page load ("Add to cart" then straight to checkout, or adding while the GET is in flight) is kept and saved rather than replaced; `e2e/saved-carts.spec.js` tests both. Only the Log out button calls `forgetCart()`; an expired session (checkout's 401) keeps the local cart. `sendCartReminders(ctx, now)` runs every minute: carts with items, `updatedAt` 1–7 days ago, no `remindedAt`, claimed by setting it with `updatedAt` in the filter; skipped if the user ordered since `updatedAt`, has `cartReminderEmails: false`, or nothing in it is active and in stock; one email, today's prices (`cartReminderEmail`).
- **Price-drop emails** (`sendPriceDropEmails()` in `routes/wishlist.js`, stage 40, run every minute from `index.js` after back-in-stock alerts): wishlist docs have `seenPrice` (the product's `price` when saved; older docs get today's price on the first sweep, without an email). Due when the product is active, `stock > 0` and `price <= seenPrice × 0.95` (`PRICE_DROP_PERCENT`), and the user hasn't `priceDropEmails: false` (`PUT /account/email-preferences`; `toUser` returns it, true when unset). One email per user per sweep (`priceDropEmail()`); each item is claimed by moving `seenPrice` to the new price with the old one in the filter (so simultaneous sweeps send once and rises don't reset it) and moved back if the send fails.
- **Back-in-stock alerts** (`routes/stockAlerts.js`): `stockAlerts` `{ userId, productId, createdAt }` (unique pair, ≤50 per user), logged-in customers only and only for sold-out products; `GET /products/:slug` includes `stockAlert`. `sendBackInStockAlerts()` runs every minute from `index.js` after `expireUnpaidOrders` (whose released stock can trigger it): alerts whose product is `active` with `stock > 0` are claimed (`sentAt`), emailed, then deleted; a failed send unsets `sentAt` for a retry, and a claim older than 10 minutes is retried. Hidden products wait until shown. Alerts can be per variant (`variantId`, via `?variant=`; the unique index is `{ userId, productId, variantId }`, missing = whole product, and `ensureIndexes` drops the pre-stage-23 `userId_1_productId_1` on startup): due when that variant's stock is above 0; an alert whose variant was deleted is removed without an email. `GET /products/:slug` returns `stockAlert` (whole product) and `stockAlertVariants` (ids). No hook on stock writes: the sweep catches admin edits, cancellations and expiries alike.
- **Low-stock email** (`lowStockEmail.js`, stage 34): `sendLowStockEmail(ctx, now)` runs from the minute sweep in `index.js` and sends once per India-time day from `SEND_HOUR` (9): it claims the day in `settings` `{ _id: 'lowStockEmail', day }` with an upsert whose filter is `day: { $ne: today }` (a second claim hits the duplicate `_id`, 11000 → `'done'`), so restarts and simultaneous sweeps send once. The list is `lowStockProducts()` from `dashboard.js` (shared with the dashboard; active products only, ≤50 listed plus "And N more"), sent with `sendToAdmins()` (`adminRecipients()`). A failed send is logged, not retried that day; no email when nothing is low. Switched off from the dashboard (`PUT /admin/dashboard/low-stock-email`, `enabled: false` on the same document; the dashboard returns `lowStockEmail`), it returns `'off'` before claiming the day, so switching back on sends that day's list. Returns `'off' | 'early' | 'done' | 'none' | 'sent'`; tests pass `now`.
- **Coupons** (`coupons.js`: checks, admin routes under `/admin/coupons` with their own `requireAdmin`): `percent` (whole rupees, rounded down, optional `maxDiscount`), `flat` or `free_delivery` (discount = the delivery charge); optional `minSubtotal`, `expiresAt`, `usageLimit`. `GET /cart?…&coupon=` returns `discount`, `coupon` or `couponError` (a reason, not an error status); `POST /orders` takes `couponCode` and re-checks it in the order transaction: `redeemCoupon` counts the use with the limit in the update filter and inserts a `couponRedemptions` doc (unique per coupon and user, so one use per customer even for simultaneous orders); `cancelOrder` calls `releaseCoupon` in its transaction to give the use back. Orders store `discount` and `coupon: { code, type }`; `total = subtotal + delivery − discount` and Razorpay charges that total. The free-delivery threshold uses the subtotal before the discount. Amounts are whole rupees so bill lines add up. Coupons are switched off, never deleted. At checkout the coupon box sits inside the order form, so it has no `name` and Enter applies the code.
- **Sales dashboard** (`routes/dashboard.js`, `GET /api/admin/dashboard?days=7|30|90`, the admin panel's index page): sales are orders `placed`/`shipped`/`delivered` by `createdAt` (unpaid and cancelled left out), revenue is `total` (after discounts, with delivery). Days are India time (`Asia/Kolkata`, a fixed +5:30 offset, also passed to `$dateToString`), the period includes today, and `daily` has every day with zeros filled in. Best-seller `sales` are item price × qty (before discounts). "To ship" counts all `placed` orders whatever their date; low stock is active products with `stock <= LOW_STOCK` (5, shared with `admin.js`). The chart is plain HTML/CSS bars (no chart library) in the `--chart` colour, with a hover tooltip and a "Show as a table" view.
- **Activity log** (`activity.js`, stage 36, collection `activity`): every admin route that changes something calls `logActivity(db, req.user, { area, action, target: { label, path }, changes: [{ field, from?, to }] })` after the change is saved, with values already written for people (`rupees()`, `yesNo()`), so old entries don't depend on later code; it never throws (a failure is logged, the change stands). Read as "{action}: {target}" (e.g. "Marked shipped: Order #100012"), so keep actions short and put the object in the target. Product saves log `productChanges(before, after, categoryName)` (variants by label) and only when something changed; state toggles (coupons, review visibility, the low-stock switch) log only a real change. The CSV import logs one entry with every change (≤100, then "And more"). `make-admin` and `reset-two-step` log with `by: null` ("Command line", filter `by=cli`). TTL index on `at`: `ACTIVITY_DAYS` (365). New admin routes must log too.
- **Writing assistant** (`ai.js`, `routes/aiWriter.js`, stage 51): "Write for me" in the admin product form. Stage 56 adds "Draft an answer" on Admin → Questions: `POST /admin/ai/answer-draft` `{ questionId }` sends the product's title, brand, category, options (variant labels, called "Options" so a sold-out one isn't read as in stock), highlights, description, up to 5 earlier visible answers and the question to `answerQuestion()` (`ANSWER_SYSTEM` says the question is customer text, never instructions), returning `{ answer, fromDetails }` (false → the page shows a warning to check the facts); it shares the `aiDraft:<userId>` hourly slot with product drafts and saves nothing. Both drafts go through `ask()` in `ai.js` (one request, error and refusal path). The fake answers an answer draft when the prompt has a `Product:` line, `fromDetails: false` for warranty questions. Admin tests click `{ name: 'Answer', exact: true }`, since "Draft an answer" also matches. `config.ai` is null without `ANTHROPIC_API_KEY` (`AI_MODEL`, default `claude-opus-5-5`; `ANTHROPIC_API_URL` only for tests), and `GET /admin/ai` tells the form whether to show the button. `POST /admin/ai/product-draft` takes `takeHourlySlot('aiDraft:<userId>', 30)` before calling Claude (failed calls use a slot too) and returns `{ description, highlights }` without saving anything; the client writes them into the form's uncontrolled textareas. `aiClient()` uses the official `@anthropic-ai/sdk` (`client.beta.messages.parse` with `betaZodOutputFormat`, `effort: 'low'`, the first upload as a base64 image if JPEG/PNG/WebP/GIF; the seed's SVG drawings are skipped), plus server-side `fallbacks: 'default'` for Opus/Sonnet (Haiku has none); errors and refusals become exposed 502s and never include the key. SDK 1.x sends the key as `Authorization: Bearer`. Tests use `server/test/fake-anthropic.js` (`startTestServer({ ai: '<model>' })`, `t.claude.calls`, `failNext(2)` because the SDK retries once, `refuseNext()`); Playwright runs it on 4102 and gives the demo server a fake key, and `demo.js` otherwise blanks the key so `npm run demo` never spends money.
- **Address book** (`addressBook.js`, stage 54): `users.addresses` `[{ _id, label, name, phone, line1, line2, city, state, pincode }]`, ≤`MAX_ADDRESSES` (10, also in `client/src/format.js`), the first is the default (`POST /account/addresses/:id/default` moves it to the front in a pipeline). `toUser` returns `addresses` and `address` (the default, or null), which `DeliveryCheck` reads. Old accounts' single `users.address` is turned into the first entry by `migrateAddresses()` from `connectDb` (rerunnable, unsets `address`). Adding refuses an exact duplicate (`hasAddress`, `$elemMatch` on the seven fields; the state is normalised first, so "karnataka" matches) and the 11th in the update filter. `POST /orders` takes `saveAddress` (default true) and calls `rememberAddress()` in the order transaction: `$push` only when no entry matches and there's room, so ordering never edits or reorders saved ones and a full book still orders. Checkout's `DeliveryAddress` shows radio cards (`addressChoice`: an id or `new`; only `new` renders `AddressFields` and the "Save it" box) and sends the chosen entry's fields via `addressFields()`; afterwards it refreshes the user from `/auth/me`. The account page scrolls to `location.hash` once the user is in (`#addresses`, `#two-step`); `.account-section` has `scroll-margin-top` for the sticky header.
- **Small photo versions** (stage 68): `client/src/photos.js` shrinks in the browser (`createImageBitmap` + canvas on a white background, so see-through PNGs don't turn black): full photos to ≤1600 px / 1 MB for reviews and products, and a 400 px / ≤200 KB small version for products (`uploadProductPhoto` uploads both; `uploadSmallVersion` never throws). The admin form accepts files up to 25 MB because of that. `POST /admin/images/:id/small` stores `images` `{ kind: 'small', of }` and sets the photo's `smallId` (replacing an older small one); `GET /api/images/:id?size=small` serves it, or the photo itself with a one-day (not immutable) cache when there's none yet. `deleteUnusedImages` keeps a small version while its photo is in use and deletes it with the photo. `smallImage(src)` in `format.js` adds `?size=small` to uploads (drawings unchanged) and is used for cards, rows, cart, wishlist, orders, return lines, gallery thumbnails, the assistant's cards and admin lists, but not the product page's big photo or link previews. `GET /admin/images/without-small` + "Make small versions" on Admin → Products backfills older product photos in the browser. Review photos have no small versions.
- **Scheduled sales** (`sales.js`, stage 67, collection `sales` `{ name, percent, categoryId | null, productIds, startsAt, endsAt, startedAt, endedAt, cancelledAt, applied, skipped }`): `runSales(ctx, now)` runs first in the minute sweep and straight after creating or ending one. Each sale is claimed (`startedAt` / `endedAt` set in a `findOneAndUpdate`), then products are changed **only in their prices**: `price` and `variants.$[vN].price` via `arrayFilters` (never the variants array, so a concurrent order's stock change isn't overwritten), MRP untouched. A product on sale has `sale` `{ id, name, percent, endsAt, regularPrice, regularVariants: [{ id, price }] }` (index on `sale.id`); starting skips products that already have a `sale` (one at a time; counted as `skipped`) and filters on the read `price`; ending restores the regular prices (variants added during the sale keep theirs; the product price is recomputed as the cheapest) and unsets `sale`. A category sale covers the category's products when it starts. `salePrice()` floors to whole rupees, at least ₹1. `assertPriceUnchanged()` makes admin PATCH refuse a changed price/MRP (product or existing variant) while on sale, 409, so the admin form's save of unchanged sale prices passes; the CSV import makes such rows errors (`onSale`). `toProductCard` and the admin product include `sale` `{ name, percent, endsAt }` (the card's "Sale" tag, the product page's `saleEndsIn()`, the form's notice). Customers get price-drop emails from the existing wishlist sweep, since a sale is a real price drop. Activity area `sales`. Tests that start sales on the shared e2e server must end them (`finally`), as other specs check prices.

Without the setting (locally, tests), `req.ip`; a header value that isn't an IP is ignored. A reset refuses the current password before using up the link. Account page (`routes/account.js`, `/api/account*`): name, address book (see below) and password change (current password via `checkPassword`, no reuse, deletes the user's other sessions but keeps this one). Email change (`/api/account/email`, `POST /api/auth/confirm-email`): needs the password (`checkPassword`, so it counts towards both login locks), then `emailChanges` holds a SHA-256 of a one-time token for the new address (24 hours, ≤3 requests per user per hour; a newer request or cancel sets `expiresAt` to now, keeping the doc for the count; TTL removes docs a day after `expiresAt`); the link is `/confirm-email#token=…` and the page confirms on a click, not on load (mail scanners). Confirming needs no login: it claims the token (`findOneAndDelete`), sets `users.email` (409 if someone took the address meanwhile, via the unique index), deletes the user's other changes and reset links (they went to the old address), keeps sessions, and emails the old address. Order emails always read the current `users.email`, nothing snapshots it. Password reset (`routes/auth.js`): `passwordResets` holds a SHA-256 of a one-time token (1 hour, TTL index, ≤3 per user per hour); hourly limits (reset links, email change requests) go through `takeHourlySlot()` (`rateLimit.js`): one `rateLimits` document per key, updated in one pipeline that drops uses older than an hour and adds this one only if there's room, so simultaneous requests can't all pass (counting documents first did, seen in CI); the link puts the token after `#` (`/reset-password#token=…`) so it never reaches server logs. `forgot-password` always answers 204 and sends in the background, so neither the reply nor its timing reveals whether an email has an account (tests poll `t.mail.sent`). Using a link deletes it (`findOneAndDelete`), all the user's other links and sessions, then logs this browser in. Roles `user`/`admin`, plus staff roles `packer`/`support` (stage 66, below); admin is only granted by `npm run make-admin`, never by the API. Two-step login (`totp.js`: RFC 6238, SHA-1, 6 digits, 30 s, ±1 step, checked against the RFC's test vectors; `twoStep.js`): `users.totp` `{ secret (base32, plaintext like the rest of the account), enabledAt, lastStep, recoveryHashes }` (recovery codes stored as `hashToken('recovery:' + code)`), `totpSetup` while confirming (15 minutes). The dashboard returns `runningOut` `{ items (≤20), total }` (rows link to the stock history, filtered to the option); `sendLowStockEmail` passes it to `lowStockEmail(products, total, publicUrl, soon)`, which shows either or both lists (subject "Running out soon: …" when nothing is low), so the email is now sent when either list has something.
- **Customers page** (`routes/customers.js`, stage 74, admins only via its own `requireAdmin`): nothing stored; `salesStages` add per-user `$lookup`s on `orders` (`SOLD`) and `returns` (`REFUNDED_RETURNS`, both from `dashboard.js`) so `spent` = sold totals − refunds, like the dashboard's revenue; the list sorts by `createdAt`, `spent` or `lastOrderAt` after those lookups (a scan per page, fine at this size) and searches name/email with `escapeRegex`. All roles are listed (staff marked). The detail adds the latest orders/returns/help requests/credit entries and counts. Goodwill credit is `grantCredit()` in `credit.js`, shared with the help request route (same checks, activity entry with the customer page as its target, and email); `CreditBox` (exported from `AdminHelp.jsx`) takes `path` (`/admin/help/:id/credit` or `/admin/customers/:id/credit`, each a GET balance + POST pair). Admin help items' `customer` has `id` (null for guests); names link to `/admin/customers/:id` on help cards and admin order pages for admins only (`can(user, '*')`).
- **Compare products** (`routes/compare.js`, stage 73): `GET /compare?slugs=` (≤`MAX_COMPARE` 3, deduplicated, active only, in the order asked) returns cards plus `category`, `highlights`, `options`, `variants` and `sameCategory`. Cards now include `categoryId`. The list is client-side (`compare.js`, a `useSyncExternalStore` over `localStorage` `bazaar.compare`: `[{ slug, title, categoryId }]`): one category at a time, so ticking a product from another category starts over (`startedOver`, shown in the tray until the next change); at 3, other ticks in that category are disabled. `CompareToggle` sits **beside** the card (the card is one link; a checkbox inside it would be nested interactive content), in `.card-with-compare` on the search page only (not rows), and on the product page next to the wishlist button. `CompareTray` (in `Layout`, an `<aside aria-label="Products to compare">`) is fixed at the bottom, clear of the assistant's button (`right: 96px`/`80px`), with a spacer so it never covers the footer; hidden on `/compare`, `/admin`, `/checkout` and printed pages. `pages/Compare.jsx` (`lazyPage`) is a table with sticky row names for phones; removing a product updates both the URL and the stored list. `/compare` is in `PRIVATE_PATHS` (endless combinations). Its ticks are named "Compare <title>", so e2e tests matching checkboxes by a product or brand name must anchor the pattern (`/^Voltix/`).
- **Store credit** (`credit.js`, stage 72): `users.credit` (paise) plus collection `creditLedger` `{ userId, change, balance (after), reason (REASONS: goodwill, taken, returned, cancelled, spent), orderId?, orderNumber?, returnId?, helpRequestId?, note?, by, at }`. **Every change goes through `addCredit(db, userId, change, entry, session)` inside the caller's transaction**: a spend has `credit: { $gte }` in the filter (409 otherwise), so concurrent orders can't overspend and the balance always equals the ledger. Credit is a **payment**, not a discount: `total`, GST invoices, coupons and dashboard revenue are unchanged; orders store `creditUsed` and `amountDue(order)` (= total − creditUsed) is what Razorpay charges (`checkoutParams`, `createOrder`, `confirmPayment`'s amount check, `refundPayment`) and COD collects (packing slips, emails; `emails.js` has its own `due()` to keep imports one-way). `POST /orders` takes `creditToUse` (what the customer was shown; refused if more than the total or the balance) and spends it after the order insert; when it covers the total, `payment` is `{ method: 'credit' }` and the order is `placed` at once (online or not). `cancelOrder` gives `creditUsed` back in its transaction (any `by`, so expiry and Razorpay refusals too), then refunds only the money part. Returns: the request takes `refundTo` (`credit`|`money`, default money); `refundSplit()` sets `refundCredit` = refund − money, where money ≤ the order's `amountDue` less the money of earlier open returns, and `refundMethod` `credit` when there's no money part. Approve adds `refundCredit` in its transaction and marks an all-credit return `refunded` at once; `refundOnline` refunds `refund − refundCredit`. Goodwill: `POST /admin/help/:id/credit` (`requirePermission('*')`, not support), whole rupees, ≤₹10,000 either way, logged (area `accounts`), emailed (`creditAddedEmail`); guests' requests can't get it. `credit.js` has its own `inTransaction` (importing `routes/reviews.js` from it would cycle through `orders.js`). `toUser` returns `credit`; checkout's "Use my store credit" (on by default) derives `creditToUse = min(balance, total)` and hides the payment choice when nothing is left to pay; a 409 reloads `/auth/me`. The account page's `#credit` section shows once there's history. Closing an account deletes the ledger (`OWN`) and forfeits the balance (the close form says how much). The order export has a "Store credit (₹)" column; the data download has `storeCredit`.
- **Announcements** (`announcements.js`, stage 71, collection `announcements` `{ text (5–160), link (a store path: starts with one `/`, no spaces; never another site, since it's on every page) | null, startsAt, endsAt, createdBy, createdAt, updatedAt }`): `currentAnnouncement()` is the one with `startsAt ≤ now < endsAt` that started last (overlaps allowed; the admin list marks the hidden one). Nothing runs on a timer: dates alone decide. A start in the past becomes now; at most `MAX_DAYS` (90). Never deleted: "End now"/"Call off" (`POST …/:id/end`) sets `endsAt` to now (and `startsAt` too if it hadn't started); edits only before the end. Activity area `announcements`. `AnnouncementBar` (in `Layout`, above the header) fetches `GET /announcement` once per page load, is an `<aside aria-label="Announcement">` (not `role="status"`: e2e tests use a page-wide `getByRole('status')`), hidden on `/admin` and invoices/credit notes and in print, and remembers a closed id in `localStorage` `bazaar.closedAnnouncement` (an edit keeps the id, so it stays closed). An announcement left on in the shared e2e server would appear on every page, so `e2e/store-announcements.spec.js` ends its own in `finally`.
- **Stock history** (`stockHistory.js`, stage 70, collection `stockHistory` `{ productId, variantId | null, label, change, after, reason, orderId?, orderNumber?, returnId?, by: { id, name } | null, at }`, TTL `HISTORY_DAYS` 365): **every stock write records entries in the same transaction**, so a new place that changes stock must too. `$inc` paths (order placement, `cancelOrder`, return approval) use `findOneAndUpdate` with `returnDocument: 'after'` (cancel and return were `bulkWrite`s before) and `movedEntry(after, variantId, change, …)`; whole saves (admin create/PATCH, CSV import) use `savedEntries(before, after, …)`, which diffs per variant by id (removed variants go to 0; switching to/from variants moves the product's own stock to/from 0). Admin PATCH now runs in `inTransaction` and diffs against `findOneAndUpdate`'s 'before', so an order between the form's read and the save isn't counted as the admin's. Reasons: `REASONS` (`ordered`, `cancelled`/`store_cancelled`/`released` from `cancelOrder`'s `by` via `CANCEL_REASONS`, `returned`, `edited`, `imported`, `added`); sales change only prices, so they have none. Customers' orders and cancellations have `by: null` (the order identifies them); `cancelOrder` takes `user` for the admin. Products with variants only get per-variant entries. `GET /admin/products/:id/stock-history` (own router, `requirePermission('stock.history')`: admins and packers) feeds `AdminStockHistory.jsx` (`/admin/products/:id/stock`), linked from the product form and, as "Stock" per item, from the admin order page (packers see item titles unlinked, as they can't open products). History starts at stage 70; seed stock has none.
- **Security headers** (`securityHeaders.js`, stage 69): `createApp` sets them on every response (API too): CSP `CONTENT_SECURITY_POLICY` (scripts only from the store and `checkout.razorpay.com`; frames, connections and images from `https://*.razorpay.com`, since Razorpay publishes no list; `style-src 'unsafe-inline'` for Razorpay's injected styles; `img-src data: blob:` for the seed drawings, favicon and QR code; `frame-ancestors 'none'`), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` switching off camera/microphone/geolocation/usb, `Cross-Origin-Opener-Policy: same-origin-allow-popups` (Razorpay's bank/UPI pop-ups), and HSTS (one year, no subdomains) only when `req.secure`. Only the production server is affected (Vite serves its own pages in dev), but the e2e server serves the build, so **anything new loaded from another address (a script, font, image host, API called from the browser) must be added to the policy** or it's blocked. A blocked load is reported by `watchSecurityPolicy()` (`errorReports.js`, from `main.jsx`) as error-report kind `blocked` ("Blocked by <directive>: <origin>", extension noise skipped); `e2e/security-headers.spec.js` checks pages for violations and answers its own report in the browser so the shared server's error list stays clean. The payments stub "pays" through `https://api.razorpay.com/test/pay`, routed to the stand-in, because a page fetch to `localhost:4101` is blocked.

**Link previews** (`preview.js`): in production `index.js` serves `client/dist` with `express.static(…, { index: false })` and then `previewRouter`, which sends the built `index.html` (read once at startup) with `<title>` and Open Graph/Twitter tags for every page: the product's for `/p/:slug` (404 for unknown or hidden products), the store's otherwise. Absolute URLs come from the request (`req.protocol` is https behind Render via trust proxy). Previews can't show SVG, so only uploaded photos (`/api/images/…`) are used; otherwise `client/public/og-image.png` (1200×630, our own drawing, made with Playwright; no emoji artwork). Everything is HTML-escaped. The product page also renders a React 19 `<title>` for the tab. Vite's dev server doesn't use this (it serves its own index.html); the e2e server serves the build, so `e2e/previews.spec.js` checks the raw HTML. **For search engines** (same router, so also production only): product pages add a `<link rel="canonical">` and a schema.org `Product` in `<script type="application/ld+json">` (`productJsonLd()`: prices as rupee strings like `"349.00"`, an `AggregateOffer` range when variant prices differ, `InStock`/`OutOfStock` from `stock`, `aggregateRating` from `rating`, only uploaded photos); every `<` in that JSON is written `\u003c` so a title can't close the script. `/robots.txt` disallows `PRIVATE_PATHS` (admin, account, cart, checkout, orders, login pages, `/api/`) and names `/sitemap.xml`, which lists `/`, `/search?category=<slug>` per category and every active product with `updatedAt` as `lastmod`; both use the request's origin like the previews, and add a page under `PRIVATE_PATHS` if it's for one visitor only. `GOOGLE_SITE_VERIFICATION` (config; letters, digits, `-`, `_` only, else ignored) adds Search Console's verification `<meta>` to every page.

**Deployment:** `render.yaml` (Render Blueprint, free plan) builds the client and runs `npm start`; every push to `main` deploys the live site. `GET /api/health` pings the database for Render's health check, and `app.set('trust proxy', 1)` makes the session cookie `Secure` behind Render's HTTPS proxy. Secrets are set in Render's dashboard (`sync: false`), never in the file. The free plan sleeps when idle, so the unpaid-order sweep only runs while it's awake.

**Backups** (`backups.js`): `backupDatabase(db, parent)` writes one `<collection>.jsonl` per collection (canonical Extended JSON per line via the driver's `BSON.EJSON`, so ObjectIds, dates and `Binary` photos round-trip) plus `manifest.json` (format, database, counts), dir 0700 / files 0600, skipping `NOT_BACKED_UP` (sessions, loginAttempts, passwordResets, emailChanges). `restoreDatabase(db, dir)` empties each collection in the manifest and re-inserts (not one transaction; rerunnable; checks counts). The CLI resolves paths from `INIT_CWD`, refuses a `BACKUP_DIR` inside the repo, describes a restore without connecting unless `--yes`, backs up the current data before restoring, and on a failed connection prints only the error's kind (the driver's message names the host). Running a backup against Atlas only reads it; tests use temp folders and the in-memory database.

**Tests never touch Atlas.** `server/test/helpers.js` starts a fresh `MongoMemoryReplSet` per test file, seeded with the sample catalog (MongoDB version pinned under `config.mongodbMemoryServer` in the root `package.json` to match the Atlas cluster, currently 8.0.34; binaries cache in `~/.cache/mongodb-binaries`). The e2e webServer runs `server/src/demo.js` on port 4100 (in-memory replica set + seed), shared by all spec files, so `shopping.spec.js` registers unique emails and buys only high-stock items the catalog tests don't count. API tests use `t.browser()` from `helpers.js` for a client with its own cookie jar; `startTestServer({ razorpay: true })` adds a stand-in Razorpay (`server/test/fake-razorpay.js`, `t.fake`: `pay()`, `webhook()`, `failNext()`), and `t.webhook()` posts signed webhooks. Playwright also starts that stand-in on port 4101 and gives the demo server its fake test keys via env (so keys in `server/.env` are never used); `payments.spec.js` replaces Razorpay's checkout.js with a stub that pays through it. `demo.js` also creates the admin `admin@bazaar.demo` / `demo-admin-123` (in-memory only), which `store-admin.spec.js` logs in as; that file is named to run after `catalog.spec.js` because it adds products and categories, as is `reviews.spec.js` (reviews change ratings; it only buys and reviews `learning-to-code-with-javascript`). `demo.js` sets `MONGODB_URI` before `config.js` loads `.env`, and env vars take precedence over the file, so a real URI in `.env` is never used there.

**Seed data** (`server/src/seed.js`): 6 categories and 38 products (Stride Running Shoes and Urbane Women Kurta Set with sizes, Ziva Women Handbag with colours that have their own photos, Urbane Men Slim Fit Jeans with Colour × Waist (no Black 34, Blue 30 sold out); whose cheapest price and total stock match their rows, so counts are unchanged) with fictional brands; 5 products are out of stock. Images are inline SVG data URIs (category icon + brand), so nothing depends on the network. Tests rely on these exact counts.

**Client** (`client/src/`): React 19 + React Router 8 in declarative mode (`BrowserRouter`/`Routes` from `react-router`; there is no `react-router-dom` in v8). Pages in `pages/`, shared pieces in `components/`.

- **URL is the state** for search/filters/sort/page (`useSearchParams`); changing a filter resets `page`. URL prices are rupees; `Search.jsx` converts to paise for the API.
- **Code splitting** (stage 39): `main.jsx` loads `pages/admin/AdminRoutes.jsx` (every admin page with its own `<Routes>` under `admin/*`, so add new admin pages there; one lazy load, not one per page plus the layout, which made fresh admin loads wait twice), `Invoice`, `ReturnRequest` and `Account` with `lazyPage()`; `TwoStepSection` imports `qrcode` only when setting up. `lazyPage()` renders the page directly once its file is in, and `OPENED_ON` preloads the one the browser opened on before the first render (no "Loading…" step; React keeps a Suspense fallback up at least 300 ms). Shared helpers belong in modules like `format.js`, not in a lazy page (a static import of one puts it back in the main file; `hasInvoice` moved for that). `Layout` wraps the `Outlet` in `PageError` (an error boundary, keyed by path) and `Suspense`. A failed page load reloads once (`reloadOnce()`, at most once a minute via `sessionStorage` `bazaar.reloadedAt`), then shows "This page didn't load" (`e2e/loading.spec.js` blocks the file to check both). In production `/assets/*` (hashed names) is served `immutable` for a year and a missing one is a plain 404 (never the app's HTML).
- `request()` (`api.js`) reads a non-JSON body as `{}` but rethrows when the request was cancelled mid-body; before stage 36 that cancellation also read as `{}`, which `useFetch` then showed as the page's data (it crashed the activity page when a filter changed quickly).
- `useFetch(path)` loads data, aborts stale requests, and derives `loading` instead of setting state in effects (the react-hooks lint rule forbids that). Inputs that must reflect the URL are uncontrolled and remounted with a `key` (header search box, price filter) rather than synced with effects.
- **Recently viewed** (`recent.js`, stage 33) is the same kind of store over `localStorage` `bazaar.recent` (slugs, newest first, ≤10), written by the product page in an effect once the product has loaded; `RecentlyViewed` asks `GET /api/recently-viewed?slugs=` for fresh cards (hidden products drop out there, not from storage) and renders nothing when there are none. `GET /products/:slug/related` scores same category 2 + same brand 1, then in stock, then `rating.count`. `GET /products/:slug/bought-together` (stage 55) aggregates the product's latest 1000 sold orders (`SOLD` statuses, kept as a local copy in `catalog.js` because importing `dashboard.js` there makes an import cycle that breaks the demo server but not the API tests), groups the other items by product with distinct orders and customers, keeps those with ≥`BOUGHT_TOGETHER_CUSTOMERS` (2, so one person's basket never shows), active and in stock, ranked by customers, orders, `rating.count`; ≤6. Index `orders { 'items.productId', createdAt }`. The product page shows it above Similar products only when it has items; `e2e/related.spec.js` buys the mixer grinder with the book as two customers. Both rows use `ProductRow` (a `region` named by its heading; e2e tests find rows with `getByRole('region', { name })`), with cards a fixed 180px wide.
- **Cart** (`cart.js`) is a `useSyncExternalStore` over localStorage (`bazaar.cart`, `[{ productId, qty }]`), synced across tabs; it never holds prices. **Login state** (`auth.jsx`): `useAuth().user` is `undefined` while checking, `null` when logged out; pages that need login render `<Navigate to="/login?next=…">`. React Router 8 navigations are transitions, so after clearing the user a page must render its own redirect (see logout in `Orders.jsx`) rather than call `navigate()`.
- **Buy again** (stage 49, client only): the order page quotes the order's lines with `GET /cart` and adds those still buyable through `addLines()` (`cart.js`: one update, a line already in the cart keeps the larger quantity, lines past `MAX_CART_ITEMS` come back), each at most its stock; `notAddable()` reads the quote's `problem` (no product or "No longer available" → no longer sold, "Out of stock", or a product that has variants since → "choose a size"). It then navigates to `/cart` with `state.boughtAgain` for the cart's notice; with nothing addable it stays on the order page with an error. `e2e/store-buy-again.spec.js` adds its own products (one sold out, one hidden), so it's named to run after `catalog.spec.js`.
- **Invoices** (`pages/Invoice.jsx`, routes `/orders/:id/invoice` and `/admin/orders/:id/invoice` with `admin`): built in the client from the order API (no server code); only `hasInvoice()` statuses (placed/shipped/delivered). The `@media print` block in `styles.css` hides the header, footer, admin tabs, breadcrumb and anything `.no-print`, and forces black on white even in dark mode.
- **Accessibility** (stage 46): `e2e/accessibility.spec.js` runs axe (WCAG 2.1 A/AA) on every page in light and on a set in dark; a new page should be added to its lists. Colours that carry text are chosen for 4.5:1: `--muted` (#5f6672 light) on every light background, `--accent-strong` for accent text on `--accent-soft` (status badges, selected tabs, notice links), `--rating` (#15803d) behind white text in both themes, `--brand` for the invoice's store name (light blue in dark, navy in print). Links inside a `<p>` are underlined. A picture link next to a link with the same target is `tabIndex={-1}` + `aria-hidden`.
- `.sr-only` labels are absolutely positioned: inside a horizontally scrolling box (admin tables) that box needs `position: relative`, or they widen the whole page on phones (`store-admin.spec.js` checks page width at 390px).
- Filter checkboxes update after navigation completes, so e2e tests click and then assert `toBeChecked()` instead of using `check()`.
