# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

npm workspaces monorepo (`server`, `client`). Run everything from the repo root. Node >= 22.12 is enforced (`engine-strict`); CI uses Node 24.

```bash
npm run demo           # API on :4000 against an in-memory MongoDB with sample data + Vite on :5173
npm run dev            # same, but against MONGODB_URI from server/.env (Atlas)
npm test               # server API tests (node:test, test/**/*.test.js)
npm run test:e2e       # Playwright browser tests (e2e/)
npm run lint           # ESLint
npm run format:check   # Prettier check; CI fails on unformatted files
npm run seed           # load the sample catalog into MONGODB_URI (skips if products exist; -- --force replaces)
```

Single tests: `npm test -w server -- --test-name-pattern="sorts by price"`, `npx playwright test -g "paginates"`.

CI runs lint → format:check → test → build → test:e2e. Prettier: single quotes, 120 columns.

The API uses port **4000** (not 3001) so it can run next to the user's task-manager project.

Project skills in `.claude/skills/`: **run-store** (launch and check the app in the browser), **add-feature** (conventions and checklist for new stages), **atlas-troubleshooting** (diagnose the Atlas connection without revealing `server/.env`). Project agent in `.claude/agents/`: **demo-verifier** (read-only tester that runs the demo, checks the UI and reports PASS/FAIL).

## Hooks

`.claude/settings.json` runs these scripts from `.claude/hooks/` (Node, no dependencies):

- **guard-env.mjs** (before Read, Grep, Bash): blocks reading or printing `server/.env` and its copies (`cat`/`head`/plain `grep`/Read tool, `echo $MONGODB_URI`, `console.log(…MONGODB_URI…)`), `git add` of an env file, and any `git commit`/`push` while an env file is staged or tracked. Count-only and masked checks (`grep -c`, `wc`, `test -f`, awk structure listings) stay allowed for the atlas-troubleshooting skill. It is a guardrail for common commands, not a sandbox.
- **confirm-destructive.mjs** (before Bash): asks the user before `npm run seed -- --force` (replaces the Atlas catalog), force pushes (`--force`, `-f`, `--force-with-lease`, `+refspec`) and `git reset --hard`.
- **format-file.mjs** (after Edit, Write): runs the repo's Prettier on the changed file; on a syntax error it reports Prettier's message back instead of failing silently.

If a hook blocks something you need, explain why to the user rather than working around it. Review or disable hooks with `/hooks`.

## Architecture

The store is being built in stages (see README): catalog, accounts/cart/checkout, the admin panel, Razorpay payments (test mode), reviews/wishlist, order emails and password reset are all done, and it is deployed on Render. Ideas not built yet, and ones set aside, are in `ROADMAP.md`: when one is built, move it to its Done table with the commit; when suggesting what's next, add new ideas there.

**Server** (`server/src/`): `createApp(ctx)` in `app.js` mounts one router per area (`routes/*.js`), each a function of `ctx = { db, client, config, razorpay, mail }` (MongoDB `Db`, `MongoClient` for sessions/transactions, config, Razorpay client or null, mail client). `index.js` loads config (`config.js` reads the gitignored `server/.env`; real env vars win), connects (`db.js` also creates indexes), and serves `client/dist` in production.

- **Money:** every price is an integer number of **paise**, in the database, the API and client state. Format only at display time (`client/src/format.js`). Never store rupees or floats.
- **Validation:** request input goes through zod schemas via `parse()` in `http.js`, which turns the first issue into a 400. Handlers are async (Express 5 forwards rejections) and throw `HttpError(status, msg)`.
- **Ids and URLs:** documents use MongoDB ObjectIds (exposed as hex strings); products and categories are addressed by unique `slug`.
- **Search** (`searchTerms`/`searchStages` in `routes/catalog.js`): each word (lower-cased, plural `s`/`es` dropped, plus a few `SYNONYMS` such as phone → mobile) must match the title, brand, a highlight or the category name, from the start of a word (escaped regex), so "book" doesn't find "Chromebook". All words must match: no partial results. With a search, the `relevance` sort ranks by `searchScore` (per word: title or brand 4, category 3, highlight 1; the whole phrase in the title +5), then popularity (`rating.count`); without one, it is popularity, labelled "Popularity" instead of "Relevance" in the UI. Search is a regex scan, fine at this catalog size. The brand facet is computed without the brand filter so other brands stay selectable.
- **Inactive products** (`active: false`) are hidden from listing and detail endpoints, and refused at checkout. Admins never delete products (orders reference them), only hide them.
- **Admin** (`routes/admin.js`): `router.use('/admin', requireAdmin)` guards everything under `/api/admin` (401 logged out, 403 customers). Product and category slugs are made once from the title/name (`slugify` from `seed.js`, numbered on clashes) and never change. Products without images get a generated SVG placeholder (`image()` from `seed.js`). Order search by number matches the end of the id via `$expr`/`$toString` (a scan; fine at this size).
- **Payments** (`payments.js`, `razorpay.js`, `routes/payments.js`): Razorpay over plain `fetch` (no SDK); `config.razorpay` is null without keys (COD only) and startup refuses non-`rzp_test_` keys. An online order is created `awaiting_payment` with stock reserved and `expiresAt` (30 min); the Razorpay order is created after the transaction (on failure ours is cancelled). It becomes `placed` only via `confirmPayment()` (checks order id, amount, captures if `authorized`), reached from the browser (signature verified), "check again" (`syncPayment`), or the webhook (raw body kept by `express.json`'s `verify` for the HMAC) — all idempotent. `expireUnpaidOrders` runs every minute from `index.js` and syncs with Razorpay before cancelling (`cancelledBy: 'system'`); `cancelOrder` refunds paid orders after its transaction (`refundPayment` claims `payment.status` first; failures → `refund_failed`, admin retry). Razorpay pays refunds from the account balance, which is short of each payment by its fee, so a full refund it can't cover comes back as a bare "invalid request sent" 400 (seen with real test keys); `refundError` therefore names Razorpay's reason plus a balance hint, and only admin responses include it (`toOrder(doc, { admin: true })`). A refund Razorpay accepted is still `pending` on its side for days, so the UI says "refund started". A payment arriving for a cancelled order is refunded. `payment` is `{ method: 'cod' }` or `{ method: 'razorpay', status, razorpayOrderId, … }`; old orders stored the string `'cod'` (normalized in `toOrder`). `HttpError(…, { expose: true })` lets a 502 message reach the client.
- **Reviews** (`routes/reviews.js`; admin list/hide in `admin.js`): only customers with a `delivered` order containing the product can review it, one review per (product, user) (unique index); `author` is a shortened name ("Asha R."). The sample catalog's ratings have no review documents, so `changeRating()` keeps them as `ratingBase` (copied from `rating` on the first change) plus `reviewStats` `{ sum, count }` of **visible** reviews, and recomputes `rating` in one update pipeline; every review write, delete and admin hide/show runs it in the same transaction (`inTransaction`). Hidden reviews stay hidden when edited and leave the rating; only a real hide/show state change moves it.
- **Wishlist** (`routes/wishlist.js`): a `wishlist` collection of `{ userId, productId, addedAt }` (unique pair, ≤200 per user); hidden products are left out of the list, not removed. `GET /products/:slug` includes `wishlisted` for the logged-in visitor.
- **Order emails** (`emails.js` templates + `sendOrderEmail()`, `mail.js` Brevo client over `fetch`): sent after the change is saved, from the four status changes: `placed` (COD in `POST /orders`; online only in `confirmPayment()` when it actually moves the order, so repeats send nothing), `shipped`/`delivered` (admin status route), `cancelled` (inside `cancelOrder()`, after any refund, so it can say "refund started"; `notify: false` when Razorpay refused the order at checkout). `sendOrderEmail` never throws: a mail failure is logged and the order change stands. Without `BREVO_API_KEY` the client only logs subject and recipient; `demo.js` blanks the key so demo/e2e accounts are never emailed. Links use `config.mail.publicUrl` (`PUBLIC_URL`). Tests use a recording stand-in (`t.mail.sent`, `t.mail.failNext()`).
- **Back-in-stock alerts** (`routes/stockAlerts.js`): `stockAlerts` `{ userId, productId, createdAt }` (unique pair, ≤50 per user), logged-in customers only and only for sold-out products; `GET /products/:slug` includes `stockAlert`. `sendBackInStockAlerts()` runs every minute from `index.js` after `expireUnpaidOrders` (whose released stock can trigger it): alerts whose product is `active` with `stock > 0` are claimed (`sentAt`), emailed, then deleted; a failed send unsets `sentAt` for a retry, and a claim older than 10 minutes is retried. Hidden products wait until shown. No hook on stock writes: the sweep catches admin edits, cancellations and expiries alike.
- **Images** (`routes/images.js`): admin uploads are raw request bodies (not multipart), checked by magic bytes, ≤1 MB, stored as `Binary` in the `images` collection and served from `/api/images/:id` with immutable caching; products store those URLs. Unused uploads are not cleaned up yet.
- **Transactions:** placing and cancelling orders use multi-document transactions (`client.startSession()` + `withTransaction`), which need a replica set. Atlas is one; tests and demo use `MongoMemoryReplSet`. Stock is decremented with the check in the filter (`stock: { $gte: qty }`); a short item throws inside the transaction so nothing changes.
- **Auth:** `sessionMiddleware` (`auth.js`) sets `req.user` from the `sid` cookie on every API request; `requireUser` guards routes. Sessions are stored as a SHA-256 of the token with a TTL index on `expiresAt`. Passwords use `scrypt` (`scrypt$salt$hash`). Login protection (`checkPassword()` in `auth.js`, used by login and the account page's password change): every attempt is stored in `loginAttempts` (keyed by a hash of the email, known or not; TTL) before the password is checked, so concurrent guesses count; more than 5 within 15 minutes → 429, even with the right password; refused attempts are deleted so retrying doesn't stretch the lock; success or a password reset clears them. A reset refuses the current password before using up the link. Account page (`routes/account.js`, `/api/account*`): name, saved address (the `address` schema from `orders.js`; the client shares `AddressFields` with checkout) and password change (current password via `checkPassword`, no reuse, deletes the user's other sessions but keeps this one). The email can't be changed (would need confirmation). Password reset (`routes/auth.js`): `passwordResets` holds a SHA-256 of a one-time token (1 hour, TTL index, ≤3 per user per hour); the link puts the token after `#` (`/reset-password#token=…`) so it never reaches server logs. `forgot-password` always answers 204 and sends in the background, so neither the reply nor its timing reveals whether an email has an account (tests poll `t.mail.sent`). Using a link deletes it (`findOneAndDelete`), all the user's other links and sessions, then logs this browser in. Roles `user`/`admin`; admin is only granted by `npm run make-admin`, never by the API.
- **Orders:** the cart is client-side; `GET /api/cart` quotes it, and `POST /api/orders` re-reads prices and stock, refusing (409) if the total differs from the `expectedTotal` the customer saw. Orders snapshot item title/price/image, so later product edits don't change them. Delivery rule lives in `orderTotals()` (`routes/orders.js`). Statuses: `placed` → `shipped` → `delivered`, or `cancelled` (customers only while placed; admins while placed or shipped), each step guarded by the expected current status in the update filter and stamped (`shippedAt`, `deliveredAt`, `cancelledAt` + `cancelledBy`). `cancelOrder()` is shared by both. Other users' orders return 404, not 403. Order numbers (`number`, from 100001) come from the `counters` document `orderNumber`, incremented inside the order transaction so failed orders leave no gaps; orders from before numbering have none and the client shows the end of the id (`orderNumber()` in `format.js`). The last address used is saved on the user.

**Deployment:** `render.yaml` (Render Blueprint, free plan) builds the client and runs `npm start`; every push to `main` deploys the live site. `GET /api/health` pings the database for Render's health check, and `app.set('trust proxy', 1)` makes the session cookie `Secure` behind Render's HTTPS proxy. Secrets are set in Render's dashboard (`sync: false`), never in the file. The free plan sleeps when idle, so the unpaid-order sweep only runs while it's awake.

**Tests never touch Atlas.** `server/test/helpers.js` starts a fresh `MongoMemoryReplSet` per test file, seeded with the sample catalog (MongoDB version pinned under `config.mongodbMemoryServer` in the root `package.json` to match the Atlas cluster, currently 8.0.34; binaries cache in `~/.cache/mongodb-binaries`). The e2e webServer runs `server/src/demo.js` on port 4100 (in-memory replica set + seed), shared by all spec files, so `shopping.spec.js` registers unique emails and buys only high-stock items the catalog tests don't count. API tests use `t.browser()` from `helpers.js` for a client with its own cookie jar; `startTestServer({ razorpay: true })` adds a stand-in Razorpay (`server/test/fake-razorpay.js`, `t.fake`: `pay()`, `webhook()`, `failNext()`), and `t.webhook()` posts signed webhooks. Playwright also starts that stand-in on port 4101 and gives the demo server its fake test keys via env (so keys in `server/.env` are never used); `payments.spec.js` replaces Razorpay's checkout.js with a stub that pays through it. `demo.js` also creates the admin `admin@bazaar.demo` / `demo-admin-123` (in-memory only), which `store-admin.spec.js` logs in as; that file is named to run after `catalog.spec.js` because it adds products and categories, as is `reviews.spec.js` (reviews change ratings; it only buys and reviews `learning-to-code-with-javascript`). `demo.js` sets `MONGODB_URI` before `config.js` loads `.env`, and env vars take precedence over the file, so a real URI in `.env` is never used there.

**Seed data** (`server/src/seed.js`): 6 categories and 38 products with fictional brands; 5 products are out of stock. Images are inline SVG data URIs (category icon + brand), so nothing depends on the network. Tests rely on these exact counts.

**Client** (`client/src/`): React 19 + React Router 8 in declarative mode (`BrowserRouter`/`Routes` from `react-router`; there is no `react-router-dom` in v8). Pages in `pages/`, shared pieces in `components/`.

- **URL is the state** for search/filters/sort/page (`useSearchParams`); changing a filter resets `page`. URL prices are rupees; `Search.jsx` converts to paise for the API.
- `useFetch(path)` loads data, aborts stale requests, and derives `loading` instead of setting state in effects (the react-hooks lint rule forbids that). Inputs that must reflect the URL are uncontrolled and remounted with a `key` (header search box, price filter) rather than synced with effects.
- **Cart** (`cart.js`) is a `useSyncExternalStore` over localStorage (`bazaar.cart`, `[{ productId, qty }]`), synced across tabs; it never holds prices. **Login state** (`auth.jsx`): `useAuth().user` is `undefined` while checking, `null` when logged out; pages that need login render `<Navigate to="/login?next=…">`. React Router 8 navigations are transitions, so after clearing the user a page must render its own redirect (see logout in `Orders.jsx`) rather than call `navigate()`.
- `.sr-only` labels are absolutely positioned: inside a horizontally scrolling box (admin tables) that box needs `position: relative`, or they widen the whole page on phones (`store-admin.spec.js` checks page width at 390px).
- Filter checkboxes update after navigation completes, so e2e tests click and then assert `toBeChecked()` instead of using `check()`.
